# 自动化测试需求文档 (PRD)：活动限定配置适配器插件系统

## 1. 需求背景与目标
本系统为一个自动化测试适配插件，旨在对平台内各种“营销活动”的“会员准入限定条件”进行全自动闭环遍历测试。
系统需要实现核心逻辑：自动修改后台活动配置 -> 动态探测/制造符合与不符合条件的账号 -> 触发活动 -> 双向正反断言拦截或通过。整个过程无需人工干预，具备数据自愈和降级容错能力。

---

## 2. 核心架构与公共执行流
对于测试矩阵中的每一条配置，测试插件必须遵循以下四步闭环生命周期：
1. **配置注入**：调用后台管理 API，动态修改目标活动的准入门槛。
2. **数据供应（核心）**：动态获取一个“正向测试账号（预期成功）”和一个“逆向测试账号（预期拦截）”。
3. **活动触发**：使用正、反账号的 Token 分别请求“参与活动”接口。
4. **双向断言**：验证正向账号响应为成功（如 code == 0），逆向账号响应为被拦截（如 code != 0）。

---

## 3. 测试矩阵与数据供应算法（API 级详细设计）

### 3.1 全平台会员限定矩阵（5 个核心用例）
后台活动配置为“全平台会员”，并通过正交/交叉组合实现 5 种用例：

* **TC-01：常规全平台会员**
  * **正向账号**：调用后台用户列表，随机抽取一个已有正常会员。
  * **逆向账号**：使用未登录状态或游客账号。

* **TC-02：新注册会员**
  * **正向账号**：现场调用前台注册 API 实时注册一个全新账号，获取其 Token。
  * **逆向账号**：使用历史注册的老会员账号。

* **TC-03：全平台会员 + 随机剔除分组**
  * **逻辑**：调用分组列表接口获取随机分组 X。后台活动配置为“全平台会员并剔除分组 X”。
  * **正向账号**：捞取/确保一个“不在”分组 X 的会员。
  * **逆向账号**：捞取/确保一个“属于”分组 X 的会员。

* **TC-04：全平台会员 + 随机剔除组合标签**
  * **逻辑**：调用组合标签接口获取随机标签 Y。后台活动配置为“全平台会员并剔除组合标签 Y”。
  * **正向账号**：捞取/确保一个“没有”组合标签 Y 的会员。
  * **逆向账号**：捞取/确保一个“绑定了”组合标签 Y 的会员。

* **TC-05：全平台会员 + 随机剔除分组 + 随机剔除组合标签**
  * **逻辑**：同时随机选择分组 X 与标签 Y 进行双重剔除配置。
  * **正向账号**：账户必须满足：既不在分组 X，也没有标签 Y。
  * **逆向账号**（单点破坏断言）：
    1. 属于分组 X，但没有标签 Y（预期拦截）。
    2. 不在分组 X，但绑定了标签 Y（预期拦截）。

### 3.2 专属限定项寻号与降级算法

#### 1. 分组配置项（满足才触发）
* **寻号 API**：`/api/Users/GetPageList` 
  * **Payload**：`{"userType":0, "groupId": [目标groupId], "pageNo":1, "pageSize":20, "orderBy":"Desc", "random":123456789, "language":"zh"}`
* **执行算法（先探测，后注入）**：
  1. 调用 `/api/Groups/GetPageList` 获取所有分组列表。
  2. 遍历分组，使用寻号 API 传入 `groupId` 进行探测。
  3. **有号分支**：若响应中 `list` 不为空，随机取一个 `userId` 作为正向账号，并以此 `groupId` 配置后台活动。
  4. **无号降级分支**：若遍历完所有分组均无账号，启动“强制注入”：调用接口 `/api/Users/UpdateGroup` （Payload: `{"userId": 138793, "groupId": 2}`）将任意测试号强制划分至目标分组，作为正向账号。
  5. **逆向账号**：选择不属于该 `groupId` 的任意其他账号。

#### 2. VIP 等级配置项
* **范围限制**：限定在 VIP 1 至 VIP 4 之间。
* **寻号 API**：`/api/Users/GetPageList`
  * **Payload**：`{"userType":0, "state":1, "vipLevel": [1-4随机值], "pageNo":1, "pageSize":20, "orderBy":"Desc"}`
* **执行算法（动态轮询与熔断）**：
  1. 脚本在 1-4 之间随机选择一个等级（例如：3）。
  2. 请求寻号 API，若 `list` 有数据，则取出一个 `userId` 作为正向账号，通关。
  3. 若返回的 `list` 为空，自动切换轮询 1-4 之间的其他等级。
  4. **熔断保护**：若 1-4 所有等级经查询均无任何账号，直接跳过（Skip）此用例，不阻塞整体测试流。
  5. **逆向账号（边界取反）**：若配置为 `>= 3`，逆向账号变更为 VIP 2 或 VIP 0。

#### 3. 渠道来源配置项 (Facebook / Adjust / TikTok)
* **渠道获取 API**：
  * Facebook: `/api/Facebook/GetList`
  * Adjust: `/api/Adjust/GetList`
  * TikTok: `/api/TikTok/GetList`
* **寻号 API**：`/api/Users/GetPageList`
  * **Payload**：`{"userType":0, "state":1, "packageId": [渠道返回的id], "pageNo":1, "pageSize":20, "orderBy":"Desc"}`
* **执行算法**：
  1. 调用对应渠道的 `GetList` 接口，解析并获取激活的 `id`（即 `packageId`）和 `packageName`。
  2. 将 `packageId` 传入寻号 API，从返回的 `list` 中随机取一个 `userId` 作为正向账号。
  3. 后台活动限制同步设置为该 `packageId`。
  4. **逆向账号**：渠道来源不等于该 `packageId` 的账号（如自然流量包用户）。

#### 4. 会员充值次数配置项
* **配置条件**：固定设置为 充值次数 >= 1 次。
* **快捷复用算法（代码瘦身）**：
  * **业务关联**：系统规则中，只有充值过的会员才拥有 VIP 等级（VIP 1-4）。
  * **执行逻辑**：本步骤直接复用 VIP 等级配置项中筛选出的任意 VIP 1-4 正向账号作为本轮正向账号，无需重复调用充值或查询接口。
  * **逆向账号**：注册至今充值次数绝对等于 0 的新账号。

#### 5. 组合标签配置项
* **标签获取 API**：`/api/TagConfig/GetCompositeTagPageList`
* **用户详情 API**：`/api/Users/GetUserDetail`
* **执行算法（反向特征剥离）**：
  1. 脚本选取一个活跃的测试账号 `userId`，请求 `/api/Users/GetUserDetail`。
  2. 解析响应体中的 `tagCompositeList` 对象（组合标签数组）。
  3. 从该账号已拥有的标签数组中，随机抽取一个合法的 `tagId`（例如 `90026`）。
  4. **两端对齐**：将该 `userId` 直接指定为正向账号；同时，将后台活动的准入门槛修改为该 `tagId`。
  5. **逆向账号**：不具备该 `tagId` 特征的任意其他账号。

---

## 4. 全局工程要求与异常处理
1. **环境自愈 (Teardown)**：每个活动配置项执行完毕后，必须将测试账号的状态、分组或活动配置进行初始化还原，杜绝脏数据污染后续测试。
2. **缓存容错 (Cache Flush)**：由于后台修改配置后服务器可能存在缓存延迟，脚本在修改后台配置后，应调用“刷新缓存”接口，或强制执行 1.5 秒的线程等待（Sleep），确保配置 100% 生效后再触发活动。
3. **并发隔离**：为了防止多条线程同时修改同一个活动的配置导致冲突，针对单个活动的配置流必须采用串行执行。
