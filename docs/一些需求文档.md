# 2. 核心架构与全局拓扑设计

## A. 全局根节点（老祖宗机制）
* 在 `setup()` 阶段（有且仅执行一次），首先调用 `phoneRegister` 尝试注册顶级根用户；若失败，立刻降级调用 `emailRegister` 注册。
* 注册成功后，通过 `getUserInfo` 捞出其 `rootInviteCode` 并广播给所有 VU。

## B. 规模目标与精准人数补齐
* **基础参数**：全局总并发 500 VU，目标总计落库注册 10,000 个真实用户。
* **每 VU 任务分配（Math.floor 零头处理）**：
  * 每个常规 VU 分配的基础人数为：`baseUsersPerVu = Math.floor(Total_Users / Total_VUs)`（即 10000 / 500 = 20人）。
  * **精准补齐逻辑**：脚本必须在最后一个 VU（即 `__VU === Total_VUs`）时，将无法整除的余数（`Total_Users % Total_VUs`）全部吸收，确保最终总注册量严格等于 10,000。

## C. 严格的账号格式约束
* **单租户模式**：单次压测只会传入一个固定的租户（TenantId）和对应的国家区号。
* **手机号格式**：必须严格为 `区号 + 固定的10位数字` 形式。后面的数字部分通过字符串补齐或引用项目中的格式化工具确保严格满 10 位。
* **邮箱格式**：必须严格遵循合法的邮箱后缀规则，直接调用项目中现有的随机邮箱格式生成器。

# 3. 核心控制流逻辑设计（重点！）

## 逻辑 A：严格的“手机 -> 邮箱”双重容错与性能指标观测
在各生命周期执行注册时，严格执行以下状态机，并引入 **k6 自定义指标（Custom Metrics）**：
1. **优先执行手机注册**：调用 `phoneRegister` (setup阶段) 或 `phoneRegisterByInvite` (default阶段)。
   * 若成功 $\rightarrow$ 自定义计数器 `phone_reg_success_counter.add(1)`，进入【数据收尾与树形绑定】阶段。
   * 若失败 $\rightarrow$ **立刻切换执行邮箱注册**。
2. **降级执行邮箱注册**：调用 `emailRegister` (setup阶段) 或 `emailRegisterByInvite` (default阶段)。
   * 若成功 $\rightarrow$ 自定义计数器 `email_reg_success_counter.add(1)`，进入【数据收尾与树形绑定】阶段。
3. **双败处理**：若邮箱注册也失败：
   * **情况 1（首用户熔断）**：如果是 default 阶段绝对时间下的全局第一个迭代（即 `__VU === 1 && __ITER === 0`），说明测试环境不通，立刻调用 `exec.test.abort("First user failed. Aborting entire test.");` **强行终止整个压测任务**。
   * **情况 2 Blocks（后续用户容错）**：记录 `console.error` 日志，**直接跳过（skip）该用户**，继续推进当前层级的下一个用户。

## 逻辑 B：数据收尾与树形绑定（含认祖归宗与防御性降级）
只要任何一种方式注册成功，调用 `getUserInfo()` 接口提取出该用户的 `inviteCode` 并塞入当前层级的临时码池 `inviteCodesByLevel[currentLevel]` 中。
当脚本推进时，必须严格执行以下拓扑绑定规则：
1. **Level 1 认祖归宗**：当 `currentLevel === 0` 时，当前层级所有用户的 `parentInviteCode` **强制统一绑定为 `setup()` 传下来的 `rootInviteCode`**。
2. **后续层级正常随机绑定**：当 `currentLevel > 0` 时，从上一层码池 `inviteCodesByLevel[currentLevel - 1]` 中**完全随机**抽取一个邀请码。
3. **异常降级（池子为空）**：若上一层（`currentLevel - 1`）的邀请码池完全为空，当前用户应该**降级挂载到上一层的上一层**（即从 `inviteCodesByLevel[currentLevel - 2]` 中随机抽取）。
4. **终止跳过**：如果向上追溯发现连“上上层”也没有（已经越界超出了 Level 1），则**直接跳过这一个用户**，不进行注册。
